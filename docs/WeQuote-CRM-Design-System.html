Getting started

Figma first, CRM checked

Component dimensions, states and visual treatment follow DS – WeQuote Platform. The current CRM is used to verify how those rules appear in the working prototype.

Components + templates
Quiet by default

White and cool-grey surfaces keep attention on records, values and actions.

Pink means action

Brand pink is reserved for primary actions, current tabs and critical emphasis.

Blue means system

Blue communicates links, focus, information and selected analytical states.

Dense, not cramped

12px body text, 24px menu rows and explicit 26px / 48px control sizes support operational work.

Canonicalisation rule: Figma component structure wins. Radius, shadow and selection treatment are read per component—not normalised into one generic AI pattern. The Design Template canvas defines composition and slots; it does not override component styling. Where the CRM differs, the difference is recorded as an implementation exception.

Getting started · Classification

Atomic model for WeQuote

Atomic Design is used here as an ownership model, not as a visual style. It tells us where a rule belongs and prevents a complete page from being copied into a second one-off component.

5 reusable layers
01 · FOUNDATION

Tokens and rules

Shared values with no product behaviour by themselves.

  • Colour variables
  • Geist type styles
  • Spacing and dimensions
  • Divider and shadow effects
02 · ATOM

Smallest control

An independently styled primitive with one main responsibility.

  • Icon and logo mark
  • Button and icon button
  • Input and checkbox
  • Badge and status label
03 · MOLECULE

Small task unit

Two or more atoms combined into one repeatable interaction.

  • Menu item / accordion row
  • Dropdown option
  • Tab with count
  • Search and filter control
04 · ORGANISM

Reusable product region

A bounded area that owns layout, behaviour and internal variants.

  • Side / top navigation
  • Deal stage and card column
  • Data table
  • Modal or settings panel
05 · TEMPLATE

Content-agnostic page

Organisms arranged into stable page slots and documented states.

  • Listing
  • Pipeline board
  • Record detail
  • Settings / customization
FoundationAtomMoleculeOrganismTemplate

Classification test

QuestionIf yesWeQuote example
Is it a reusable visual value rather than UI?Foundation#F12B53, 12px body, Shadow MD
Can it stand alone as the smallest meaningful control?AtomPrimary button, checkbox, status badge
Does it combine atoms to complete one small task?MoleculeSearch input, dropdown option, tab + count
Does it own a bounded reusable region with internal layout?Organism184px Side Menu, CRM table, notification list
Does it arrange organisms into page slots without fixed business data?TemplateLead listing, deal detail, portal customization
Is it a template filled with a real customer, quote or project?Screen / example“Ocean Palm Residences” deal detail; not a new component
Boundary rule: classify by responsibility, not physical size. A 184px navigation is an organism; a full-screen frame with fixed copy is a screen. Do not make every Figma frame a component, and do not turn template data into component properties unless the data changes layout or behaviour.

Composition rules

Reuse one product shell

Page templates start after the shared Side Menu and Top Navigation; they do not clone either organism.

Name slots by responsibility

Use header, toolbar, primary content, supporting rail and contextual panel—not “left box” or “card 2”.

Preserve contextual density

CRM rows, Manage User rows and legacy dashboard tables keep their documented families rather than converging by eye.

Keep boundaries structural

Use the exact divider, border, radius and shadow belonging to the nested component or panel.

Do not template a screenshot

Fixed names, values and statuses are example data. Extract the regions and state contract, not the screenshot content.

Do not add generic AI styling

No blanket rounded cards, floating surfaces, decorative left rails or shadows unless the referenced Figma component specifies them.

Guidance

Accessibility baseline

The current CRM is visually dense, so predictable focus, readable labels and forgiving targets are especially important.

Required
Visible keyboard focus

Use the 2px blue focus ring with offset. Never remove outline without an equivalent.

Names for icon buttons

Every icon-only action needs an accessible name and visible tooltip where helpful.

Persistent field labels

Placeholders provide examples, not the only label or instruction.

Text plus colour

Status meaning requires text, icon or shape in addition to semantic colour.

Avoid tiny decision text

Do not use 7–8px metadata sizing for instructions, errors or required actions.

Avoid hover-only actions

Keyboard and touch users must be able to discover and activate the same controls.
